## 4. A/B/C 结论分层（按用户要求）

**A. 已由实际请求证实的现象**
1. 单工具 + 短 description：任意参数大小（至 237 tok）、任意嵌套、中文值、多块输出 → 原生路径 12/12 工具调用成功且 payload 精确匹配；
2. 三工具真实集（新 desc）+ AgentLoop system：三步 goal、单步指令两种措辞 → 原生与 OpenAI 兼容两条路径全部空响应（compl_tok 236~246 非零、content=""、tool_calls=null、done_reason=stop）；
3. 手工模板（ASCII 原样序列化）下新 desc 场景模型原始发射完好且 spec 结构正确；
4. E1b 旧 desc 在手工模板下的输出为结构错误的 JSON（与 R0 失败模式 B 一致）——R1 示例确实教会了模型正确结构；
5. 失败响应的生成 token 数（~236）与 E2-D 成功案例的单块大小（236）几乎相同。

**B. 根据现象推断的可能原因（未直接证实）**
1. 触发因素是**新 desc 在 Go json.Marshal 序列化后的形态**（\u 转义 + \" 转义的 1385 字符超长 schema 行 + 内嵌 JSON 示例），它使模型在真实模板下的输出偏离标准工具调用格式（可能的变体：模仿转义风格、格式微差、或在单块后附加未闭合尾块），而 Ollama 0.40.6 对非标准/不可提取的工具调用文本**静默丢弃**（不回退到 content、不报错）；
2. 模型生成了 ~236 tokens 后停止（done_reason=stop）——若其形态是"一个完整大块 + EOS"，则与 E2-D 矛盾（应成功），故更可能是某种非标准形态；具体形态不可观测。

**C. 仍无法确认的技术问题**
1. 真实 `/api/chat` 路径下模型的原始输出文本（被服务端丢弃，Ollama 日志在本机不可访问）；
2. Ollama 0.40.6 工具提取的确切失败分支（转义处理/截断块/多块边界）；
3. 更高版本 Ollama 是否修复该静默丢弃行为（未测试——遵守"不更换环境"约束）；
4. E1 手工模板与真实模板的全部序列化差异（仅确认 ensure_ascii 一项）。
